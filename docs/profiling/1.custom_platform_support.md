# Custom Platform Operator Profiling Guide

This guide is for platform engineers who need to collect operator execution times on non-CUDA accelerators (Tenstorrent, etc.) using `compute_cost_profiler_custom.py`, then train efficiency models on a CUDA machine.

---

## Overview

`syssim/compute/compute_cost_profiler_custom.py` is a platform-agnostic profiling script that works in two phases:

**Phase 1 (target platform):** The script sweeps a parameter grid on the target accelerator, runs each operator configuration, and records the median execution time (ms). It also computes roofline theoretical times from hardware peak specs to derive efficiency values. Results are written to CSV files.

**Phase 2 (CUDA machine):** Transfer the CSVs to a machine with CUDA, then use `compute_cost_profiler.py` to train XGBoost or MLP efficiency models. The output is a `.pth` file for use with the SysSim simulator.

The script supports 4 operators:

| Operator | Description | Data type |
|----------|-------------|-----------|
| `gemm` | Matrix multiplication C = A @ B | FP16 |
| `attn` | Scaled dot-product attention (supports GQA) | FP16 |
| `rmsnorm` | RMS normalization | FP32 |
| `silu` | SiLU activation | FP16 |

---

## Prerequisites

**Target platform (the machine running profiling):**

- Python 3.10+
- `numpy`, `pandas` (`pip install numpy pandas`)
- The target platform's SDK (e.g. `torch_xla`, `tt-xla`, etc.)
- No CUDA required, no CUDA build of `torch` required (unless the platform itself is based on torch_xla)

**CUDA machine (for training efficiency models):**

- A GPU with CUDA available
- Full SysSim dependencies (`pip install -r requirements.txt`)

## Step 1: Configure Hardware Parameters

Open `syssim/compute/compute_cost_profiler_custom.py` and find the hardware configuration block near the top of the file. Fill in the 5 constants:

```python
# ==============================================================================
# Hardware Info (manually specified for target platform)
# ==============================================================================

PLATFORM_HW_NAME = "unknown"              # Platform identifier, used in CSV filenames
PEAK_TFLOPS_MM = 0.0                      # Tensor unit FP16 peak throughput (TFLOP/s), for GEMM/ATTN roofline
PEAK_TFLOPS_MM_CONSERVATIVE = 0.0        # Conservative peak for small operators (used when any dimension < 512)
PEAK_TFLOPS_MATH = 0.0                   # Vector unit peak throughput (TFLOP/s), for RMSNorm/SiLU roofline
PEAK_MEMORY_BANDWIDTH_GBPS = 0.0         # DRAM bandwidth (GB/s)
```

**Parameter descriptions:**

- `PLATFORM_HW_NAME`: A string identifier that appears in the output CSV filename, e.g. `gemm_tenstorrent_wh_data.csv`. Use lowercase with underscores, no spaces.

- `PEAK_TFLOPS_MM`: FP16 peak throughput of the tensor core (matrix multiply unit), in TFLOP/s. Used for GEMM and Attention roofline calculations. Look for "FP16 Tensor TFLOPS" or "Matrix TFLOPS" in the chip datasheet.

- `PEAK_TFLOPS_MM_CONSERVATIVE`: When any of the M, N, or K dimensions in a GEMM is smaller than 512, this value replaces `PEAK_TFLOPS_MM` to reflect the real efficiency loss on small operators (kernel launch overhead, etc.). If you don't have measured data, set it equal to `PEAK_TFLOPS_MM`.

- `PEAK_TFLOPS_MATH`: Peak throughput of the vector compute unit, in TFLOP/s. Used for RMSNorm and SiLU roofline calculations. Typically much lower than the tensor unit peak.

- `PEAK_MEMORY_BANDWIDTH_GBPS`: DRAM memory bandwidth in GB/s. Look for "Memory Bandwidth" in the chip datasheet.

**Example: Tenstorrent Wormhole**

```python
PLATFORM_HW_NAME = "tenstorrent_wh"
PEAK_TFLOPS_MM = 300.0               # Example value, replace with actual spec
PEAK_TFLOPS_MM_CONSERVATIVE = 300.0  # Example value, set equal to PEAK_TFLOPS_MM if unsure
PEAK_TFLOPS_MATH = 75.0              # Example value
PEAK_MEMORY_BANDWIDTH_GBPS = 256.0   # Example value
```

## Step 2: Implement Operator Profiling Functions

The script contains 4 functions you need to implement. All currently raise `NotImplementedError`:

- `_profile_gemm(m, n, k, num_runs)`
- `_profile_attention(batch, num_heads, seq_len, head_dim, num_kv_heads, num_runs)`
- `_profile_rmsnorm(seq, dim, num_runs)`
- `_profile_silu(seq, dim, num_runs)`

**Contract for each function (must be followed):**

1. Allocate tensors on the target device
2. Run several warmup iterations to let the device finish JIT compilation
3. Synchronize the device to confirm warmup is complete
4. Timing loop: each iteration runs the operator, synchronizes, and records wall time
5. Return the median time in ms, or `-1.0` on OOM or timeout

**Critical note:** Timing must include device synchronization. If you don't synchronize before recording the end time, you're only measuring CPU-side dispatch latency, not actual execution time.

---

### (a) torch_xla platforms (Tenstorrent + tt-xla example)

torch_xla uses lazy evaluation: calling `torch.mm(a, b)` only traces the computation graph without executing it. You must call `xm.mark_step()` to trigger compilation and execution, then `xm.wait_device_ops()` to wait for completion. **If you omit these two calls in the timing loop, measurements will be near zero and completely meaningless.**

**`_profile_gemm` implementation (torch_xla):**

```python
def _profile_gemm(m: int, n: int, k: int, num_runs: int = 100) -> float:
    try:
        import torch
        import torch_xla.core.xla_model as xm

        device = xm.xla_device()

        a = torch.randn(m, k, device=device, dtype=torch.float16)
        b = torch.randn(k, n, device=device, dtype=torch.float16)

        # Warmup: let XLA finish compilation
        for _ in range(5):
            torch.mm(a, b)
            xm.mark_step()
        xm.wait_device_ops()

        times = []
        for _ in range(num_runs):
            start = time.perf_counter()
            torch.mm(a, b)
            xm.mark_step()       # Trigger execution
            xm.wait_device_ops() # Wait for completion, must come before recording end time
            end = time.perf_counter()
            times.append((end - start) * 1000)

        return float(np.median(times))

    except (RuntimeError, MemoryError):
        return -1.0
```

**`_profile_attention` implementation (torch_xla):**

If tt-xla doesn't yet support `F.scaled_dot_product_attention`, you need a manual attention implementation. Try `F.scaled_dot_product_attention` first and fall back to the manual version on failure:

```python
def _profile_attention(
    batch: int, num_heads: int, seq_len: int, head_dim: int,
    num_kv_heads: int | None = None, num_runs: int = 100,
) -> float:
    if num_kv_heads is None:
        num_kv_heads = num_heads

    try:
        import torch
        import torch.nn.functional as F
        import torch_xla.core.xla_model as xm

        device = xm.xla_device()

        q = torch.randn(batch, num_heads, seq_len, head_dim,
                        device=device, dtype=torch.float16)
        k = torch.randn(batch, num_kv_heads, seq_len, head_dim,
                        device=device, dtype=torch.float16)
        v = torch.randn(batch, num_kv_heads, seq_len, head_dim,
                        device=device, dtype=torch.float16)

        # GQA: expand KV to match Q head count
        if num_kv_heads != num_heads:
            k = k.repeat_interleave(num_heads // num_kv_heads, dim=1)
            v = v.repeat_interleave(num_heads // num_kv_heads, dim=1)

        # Define attention computation (prefer SDPA, fall back to manual if unsupported)
        def run_attn(q, k, v):
            try:
                return F.scaled_dot_product_attention(q, k, v)
            except (NotImplementedError, RuntimeError):
                # Manual implementation: softmax(Q @ K^T / sqrt(d)) @ V
                scale = head_dim ** -0.5
                scores = torch.matmul(q, k.transpose(-2, -1)) * scale
                attn = torch.softmax(scores, dim=-1)
                return torch.matmul(attn, v)

        # Warmup
        for _ in range(10):
            run_attn(q, k, v)
            xm.mark_step()
        xm.wait_device_ops()

        times = []
        for _ in range(num_runs):
            start = time.perf_counter()
            run_attn(q, k, v)
            xm.mark_step()       # Trigger execution, do not omit
            xm.wait_device_ops() # Wait for completion, must come before recording end time
            end = time.perf_counter()
            times.append((end - start) * 1000)

        return float(np.median(times))

    except (RuntimeError, MemoryError):
        return -1.0
```

## Step 3: Run Profiling

On the target platform, run each of the 4 operators separately:

```bash
python -m syssim.compute.compute_cost_profiler_custom \
    --operator gemm --output data/profiling/ --num-runs 100

python -m syssim.compute.compute_cost_profiler_custom \
    --operator attn --output data/profiling/ --num-runs 100

python -m syssim.compute.compute_cost_profiler_custom \
    --operator rmsnorm --output data/profiling/ --num-runs 100

python -m syssim.compute.compute_cost_profiler_custom \
    --operator silu --output data/profiling/ --num-runs 100
```

**Parameter grid sizes (for reference):**

| Operator | Configurations | Description |
|----------|----------------|-------------|
| `gemm` | ~262,144 | 64 x 64 x 64 (M x N x K samples) |
| `attn` | ~17,920 | 5 x 64 x 7 x 4 x 2 (bs x seq x nh x nkv x hd) |
| `rmsnorm` | ~16,384 | 128 x 128 (seq x dim) |
| `silu` | ~16,384 | 128 x 128 (seq x dim) |

GEMM has the most configurations and may take several hours on slower platforms. Run with `--num-runs 20` first to verify your implementation is correct, then use `--num-runs 100` for the full dataset.

**Output files:**

```
data/profiling/gemm_{PLATFORM_HW_NAME}_data.csv
data/profiling/attn_{PLATFORM_HW_NAME}_data.csv
data/profiling/rmsnorm_{PLATFORM_HW_NAME}_data.csv
data/profiling/silu_{PLATFORM_HW_NAME}_data.csv
```

**CSV column descriptions:**

- `gemm`: `M, N, K, t_measured_ms, t_roofline_ms, efficiency`
- `attn`: `bs, seq, nh, nkv, hd, t_measured_ms, t_roofline_ms, efficiency`
- `rmsnorm` / `silu`: `seq, dim, t_measured_ms, t_roofline_ms, efficiency`

`t_measured_ms` is the measured median time, `t_roofline_ms` is the roofline theoretical time, and `efficiency = t_roofline_ms / t_measured_ms` (closer to 1 means closer to theoretical peak). OOM configurations are recorded as `-1.0` and filtered out automatically during training.

## Step 4: Train Efficiency Models (on a CUDA Machine)

Transfer the CSV files to a CUDA machine (via `scp`, `rsync`, or any other method), then run training for each operator:

```bash
# Train GEMM efficiency model (XGBoost, recommended)
python -m syssim.compute.compute_cost_profiler \
    --operator gemm \
    --data-path data/profiling/gemm_tenstorrent_wh_data.csv \
    --output data/trained_models/gemm_tenstorrent_wh_xgb.pth \
    --backend xgboost

# Train Attention efficiency model
python -m syssim.compute.compute_cost_profiler \
    --operator attn \
    --data-path data/profiling/attn_tenstorrent_wh_data.csv \
    --output data/trained_models/attn_tenstorrent_wh_xgb.pth \
    --backend xgboost

# Train RMSNorm efficiency model
python -m syssim.compute.compute_cost_profiler \
    --operator rmsnorm \
    --data-path data/profiling/rmsnorm_tenstorrent_wh_data.csv \
    --output data/trained_models/rmsnorm_tenstorrent_wh_xgb.pth \
    --backend xgboost

# Train SiLU efficiency model
python -m syssim.compute.compute_cost_profiler \
    --operator silu \
    --data-path data/profiling/silu_tenstorrent_wh_data.csv \
    --output data/trained_models/silu_tenstorrent_wh_xgb.pth \
    --backend xgboost
```

**Two training backends:**

- `--backend xgboost` (recommended): Fast training, typically finishes in minutes, good generalization.
- `--backend mlp`: Neural network model, requires `--epochs 300`, takes longer to train, better suited for very large datasets.

The CSV already contains `t_roofline_ms` and `efficiency` columns. The training script uses them directly without recomputing.

## FAQ

**Q: I'm getting a lot of OOM errors and many configurations are recorded as -1.0. What should I do?**

The script catches `RuntimeError` and `MemoryError`, records failed configurations as `-1.0`, and filters them out during training. If the OOM rate is too high (above 30%), the training data will be insufficient. Consider narrowing the parameter grid by editing the `end` parameter in `_build_grids()`. For example, reduce the GEMM `M` upper bound from 131072 to 32768.

**Q: On a torch_xla platform, all my measured times are near zero. What's happening?**

This is the classic symptom of XLA lazy evaluation. The timing loop must call `xm.mark_step()` and `xm.wait_device_ops()` before recording the end time. Without them, you're only tracing the computation graph, not executing it. See the implementation examples in Step 2.

**Q: My platform doesn't support `F.scaled_dot_product_attention`. What do I do?**

Use a manual implementation instead:

```python
scale = head_dim ** -0.5
scores = torch.matmul(q, k.transpose(-2, -1)) * scale
attn = torch.softmax(scores, dim=-1)
out = torch.matmul(attn, v)
```

This is mathematically equivalent to SDPA, just without FlashAttention's memory optimizations. It may OOM at large `seq_len` values.

**Q: What data types should each operator use?**

| Operator | Data type |
|----------|-----------|
| GEMM | FP16 |
| Attention (Q/K/V/Out) | FP16 |
| RMSNorm (x and weight) | FP32 |
| SiLU | FP16 |

These types must match exactly. If they don't, the byte count assumptions in the roofline calculation will be wrong, causing skewed efficiency values.

**Q: What should I set `PEAK_TFLOPS_MM_CONSERVATIVE` to?**

This value applies to GEMM/Attention cases where any dimension is smaller than 512, reflecting the reality that small operators can't reach peak throughput due to kernel launch overhead and similar factors. If you don't have measured data, set it equal to `PEAK_TFLOPS_MM`. The roofline will be slightly optimistic, but it won't affect the correctness of model training.

**Q: The script throws `RuntimeError: Hardware not configured`. What's wrong?**

`PLATFORM_HW_NAME` is still set to the default value `"unknown"`, and the script refuses to run. Go back to Step 1 and fill in all 5 hardware constants.

## End-to-End Example: Tenstorrent Wormhole
