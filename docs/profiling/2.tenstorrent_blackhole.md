# Tenstorrent Blackhole Profiling Guide

This guide walks through profiling Tenstorrent **Blackhole** accelerators
(P150A, P150B, P100A) end-to-end with the unified
`syssim.compute.compute_cost_profiler` entry point. It is the Blackhole
companion to the Wormhole flow already covered in
[`1.custom_platform_support.md`](1.custom_platform_support.md).

The unified profiler covers both data collection (on a Blackhole host with
`ttnn`) and efficiency-model training (on a CUDA host). On a Blackhole host
with no CUDA you only run the profiling phase and ship the CSV elsewhere
for training.

---

## 0. What you need

**On the Blackhole host** (one or two physical cards):

- `python3` (>= 3.10).
- The TT Python stack: `ttnn>=0.69.0` (0.65.x ships slim-LTO firmware
  objects that the bundled sfpi gcc 15.1.0 cannot link), `tt-metalium`
  runtime tree.
- `numpy`, `pandas`, `pyyaml` (in `requirements.txt`).
- `tt-smi` reachable in `$PATH` (used for device sanity checks).
- A working device entry under `/dev/tenstorrent/{0,1}`. Reset with
  `tt-smi -r 0 1` after a hang.

The bundled installer covers most of this:

```bash
bash scripts/install_tt_stack.sh
```

If you suspect environment drift, dump everything we care about with:

```bash
bash scripts/probe_tt_env.sh
```

The probe prints `str(ttnn.open_device(...))` for both chip ids so you can
verify the auto-detect path picks the right entry from
`compute_cost_profiler.TT_HW_DATABASE`.

**On a separate CUDA host** (used only when training models):

- A GPU with CUDA available.
- `pip install -r requirements.txt`.

## 1. Confirm the platform name

`compute_cost_profiler.TT_HW_DATABASE` ships these per-chip Blackhole entries
(BF16 matmul peak, conservative MM peak, FP32 SFPU peak, GDDR6 bandwidth):

| Platform name   | Variant       | BF16 MM TFLOP/s | SFPU FP32 TFLOP/s | DRAM BW (GB/s) |
|-----------------|---------------|-----------------|-------------------|----------------|
| `tt_bh_p150b`   | P150B         | 387             | 16                | 512            |
| `tt_bh_p150a`   | P150A         | 387             | 16                | 512            |
| `tt_bh_p100a`   | P100A         | 332             | 14                | 224            |
| `auto_tt`       | auto-detect   | _resolved at runtime_                                |

`_auto_detect_tt_platform` matches against `str(ttnn.open_device(0))`. If your
device repr does not contain `p150a` / `p150b` / `p100` / `blackhole`, pass the
platform name explicitly with `--platform tt_bh_p150b` (or whichever matches
your chip).

---

## 2. Profile the four operators on Blackhole

Run on the Blackhole host. Each call profiles one operator across the
parameter grid in `TT_COMPUTE_GRIDS` and appends rows to a CSV that supports
resume — re-running picks up where the previous run stopped.

```bash
# Smoke-test with a tiny run-count first
python -m syssim.compute.compute_cost_profiler \
    --operator gemm \
    --platform tt_bh_p150b \
    --csv-output-dir data/profiling/ \
    --num-runs 5

# Full profiling sweep
python -m syssim.compute.compute_cost_profiler \
    --operator all \
    --platform tt_bh_p150b \
    --csv-output-dir data/profiling/ \
    --num-runs 100
```

Equivalent for the smaller P100A:

```bash
python -m syssim.compute.compute_cost_profiler \
    --operator all \
    --platform tt_bh_p100a \
    --csv-output-dir data/profiling/ \
    --num-runs 100
```

Outputs:

```
data/profiling/gemm_tt_bh_p150b_data.csv
data/profiling/attn_tt_bh_p150b_data.csv
data/profiling/rmsnorm_tt_bh_p150b_data.csv
data/profiling/silu_tt_bh_p150b_data.csv
data/profiling/profiling_manifest.yaml
```

The manifest is updated atomically with each operator and is the file the
training step in section 4 reads.

OOM configurations are recorded as `t_measured_ms = -1.0` and filtered out at
training time. Failed configs do not abort the sweep.

---

## 3. (Optional) auto-detect the platform

If the host has only one Blackhole variant installed, you can let the profiler
pick it:

```bash
python -m syssim.compute.compute_cost_profiler \
    --operator all \
    --platform auto_tt \
    --csv-output-dir data/profiling/ \
    --num-runs 100
```

This calls `_auto_detect_tt_platform`, which returns one of `tt_bh_p150b`,
`tt_bh_p150a`, `tt_bh_p100a`, `tt_wh_n300`, or `tt_wh_n150`. If detection
fails, the profiler logs a warning and defaults to `tt_wh_n300` — pass
`--platform` explicitly to avoid that footgun on Blackhole hosts.

---

## 4. Train efficiency models on a CUDA host

Copy the CSVs to a CUDA-capable host and train per operator:

```bash
for op in gemm attn rmsnorm silu; do
    python -m syssim.compute.compute_cost_profiler \
        --operator "$op" \
        --data-path "data/profiling/${op}_tt_bh_p150b_data.csv" \
        --output "data/trained_models/${op}_tt_bh_p150b_xgb.pth" \
        --backend xgboost
done
```

XGBoost is the recommended backend (fast, low variance). For very large
datasets switch to `--backend mlp --epochs 300`.

---

## 5. Use the trained models in SysSim

Once the four `.pth` files exist, point `SimulatorConfig` at the matching
hardware entry:

```python
from syssim import SimulatorConfig
from syssim.config import HardwareInfo
from syssim.compute.compute_cost_profiler import TT_HW_DATABASE

mm, mm_cons, math_t, bw = TT_HW_DATABASE["tt_bh_p150b"]
hw = HardwareInfo(
    peak_tflops_mm=mm,
    peak_tflops_math=math_t,
    peak_memory_bandwidth_gbps=bw,
    peak_tflops_mm_conservative=mm_cons,
)
config = SimulatorConfig(hw_info=hw)
```

Pass that `config` to `trace_model_for_inference` /
`trace_model_for_training` and the simulator will use the Blackhole roofline
plus the trained efficiency models for time predictions.

## 6. Common pitfalls

- **Wrong device repr** — if `str(ttnn.open_device(0))` does not contain
  `blackhole` / `p150` / `p100`, auto-detect silently routes to Wormhole.
  Either pass `--platform tt_bh_p150b` explicitly or extend
  `_auto_detect_tt_platform` with the new substring.
- **Card with two chips** — P150B exposes two devices. The profiler opens
  device 0 by default; close it between runs (`tt-smi -r 0 1` if it hangs).
- **Stale kernel cache** — after a `ttnn` upgrade, clear
  `~/.cache/tt-metal-cache/` to avoid running pre-built kernels against a
  newer runtime.
- **Lustre filesystems for builds** — never build the TT-Metal tree on
  Lustre; build under `/tmp` and symlink kernel sources back. (See the
  `tenstorrent-remote` skill for the exact recipe.)
- **DRAM bandwidth claims** — published peaks (512 / 224 GB/s) are
  upper bounds. If your measured efficiencies hover near 1.0 across the
  bandwidth-bound operators, lower `peak_memory_bandwidth_gbps` in
  `TT_HW_DATABASE` and re-train.
